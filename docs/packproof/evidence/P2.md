## Implementation

- Supabase Auth password sign-in uses an HttpOnly, SameSite=Strict cookie; Node validates the access token with `/auth/v1/user`. Anonymous P1 investigations remain available. Operator-assigned shop accounts cannot be claimed through signup. Three fictional demonstration accounts are provisioned; credentials stay in ignored owner-only `.local/p2/demo-accounts.json`.
- Enrollment challenges bind authenticated account, actor, nonce, key ID and expiry. The browser persists a nonextractable P-256 key in IndexedDB, signs proof of possession and retains the matching key across interrupted enrollment. One active device per actor; replacement/revocation blocks pending sessions. Registration is not hardware attestation.
- Strict H4 agreements hash the exact server-issued payload bytes and bind the unit, parties, keys, owner/version, mapping, policy and expiry. Transfer writes use the restricted NOLOGIN `packproof_transfer` role, forced RLS, participant checks and actor/operation/exact-body-hash idempotency. Rate accounting uses a separate short transaction, counts failed attempts and releases the actor counter before signature/evidence checks.
- Both QR directions use signed, nonce-bound frame batches and 128-bit opaque handles stored in PostgreSQL. Animation is local at a 5 updates/s target, with no polling/signing loop. Three consecutive distinct valid frames reserve a direction exactly once. Discovery occurs before collecting the fresh scan sequence. Batches include signing/upload preparation time and shorten within the unchanged 120-second session. Separate consents last at most 30 seconds; accepted frames are checked at trusted server receipt time, including during later human review.
- Seller authorization, exact mapping, original signed issuance, current ownership chain, lifecycle, policy, scoped issuer authority/revocation, active keys and fresh restricted authorization snapshot are independently checked under transaction locks. Shop A receives the exact required refusal. A privileged, nonpublic commit function independently enforces owner/version/key/policy/challenge constraints, appends immutable signed approvals and increments ownership once. Signed cancellation binds the unchanged agreement and enrolled device.
- A durable receipt outbox separates ownership from signing. Failure/retry affects only receipt generation. GET and idempotent confirmation recover the same accepted transfer. The UI uses “Transfer recorded; receipt preparing.” Receipts include exact agreement bytes/hash, both device consents, scan proofs, versions, commit time and restricted source references. The browser verifies the trusted signer and both device approvals before download.
- `/chainproof` provides both participant flows, account/device status, agreement review, QR display/scanning, expiry, cancellation and receipt recovery. Camera denial offers status recovery without bypassing QR verification. Physical association remains unresolved; there is no authenticity, legal-title or proximity claim.
