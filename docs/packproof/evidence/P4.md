## Contracts and trust

The exact schemaVersion 1 `.packproof.json` envelope contains only `schemaVersion:1`, `manifestJws`, `directoryJws`, `records:[{id,jws}]` and `media:[{sha256,mime:'image/jpeg',base64}]`. Existing H7 manifest fields bind selection, namespace, profile/dataset, coverage, sequence, times, exact compact-JWS hashes/dependencies and media sizes/hashes. Public-demo profile `packproof-public-demo-1`, dataset generation `packproof-demo-1`. Imports have a strict 2 MiB byte limit, bounded JSON depth 16/collections/nodes/strings, 128 records, 3 selected units and 8 media entries; cumulative local storage is also bounded. Exported packs currently omit media entirely.

A root-signed P4 directory envelope carries the existing unchanged root-signed issuer audit chain plus an explicit **pack** grant, restricted to `pack-manifest` and `public-custody-snapshot`. The separate pack key cannot issue products or commit transfers. It is encrypted, server-only in Production under explicit user approval. Root/product-issuer keys stay in ignored offline operator storage; the receipt-only signer is unchanged. `p4-authority.json` records public key IDs and the grant policy. Directory/snapshot freshness is 24 hours; this is a demo evidence policy, not a safety standard. Current directory expires **2026-11-04T18:30:04.173Z**. Renewal requires an explicit append through the offline operator; old signed snapshots/claims are never rewritten or renewed.

Official HTTPS setup verifies the directory against the compiled pinned root, records server time/directory/hash/sequence floors and installs public viewer assets. A peer pack cannot establish or replace a root. Uninitialized/cleared state says: “Trusted setup required. Connect to the official PackProof application.” Production bootstrap is restricted to the permanent origin; localhost is permitted for software tests.

Verification order: bounded JSON/schema → existing trusted setup → root directory signature/hash → narrow pack grant/signature → exact bytes and media hashes → complete dependencies → existing record-specific issuer authority/signatures → item/mapping/notice scope → persistent sequence/known adverse and ownership/allocation conflicts → freshness limitations. Existing shared `verifyRecordSet` validates original issuer claims. Pack-role signatures validate only the separately dated public projection. There are no import URL fetches, model calls or HTML execution; imported text uses `textContent`.

The authenticated exporter checks the full actual signed owner/receipt chain internally in a consistent database transaction, then signs a new public snapshot with an item-scoped limited holder reference and actual owner revision. Restricted receipts, current private account/device/agreement IDs, photos and credentials never enter the pack. The projection attests to the server's dated view, with current ownership explicitly not rechecked offline. Actual FP-1002 remains owner version 2 with its original one accepted handover and jointly signed receipt.

All imports stage before a single strict-durability IndexedDB transaction with epoch conflict detection. Validation/transaction failure preserves previous packs. Previously accepted signed records, warnings, gaps, revocations and higher scoped sequences remain known across partial imports and reloads. Conflicting ownership and second allocations/mappings for a known unit fail. A backwards/unreliable clock cannot establish freshness. Expired valid evidence is historical; future notices/revocations, physical association, current ownership, legal title, safety and genuine-product certainty remain unresolved.

## PWA and acceptance

The standalone local verifier is built with existing esbuild/jose/Zod; native IndexedDB stores accepted public packs. No new dependency or lockfile. A `/offline/` service worker caches only 6 exact same-origin public assets (HTML, bundled verifier, CSS, 2 icons, manifest). Private API responses/authentication/pack files are never cached in CacheStorage. Required assets use local system fonts; no runtime CDN, server rendering or auth refresh is needed to open the cached viewer. The same app manifest starts at the cached viewer; online navigation still reaches Investigator, Handover, Inspector and tools.
